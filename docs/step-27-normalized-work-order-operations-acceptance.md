# 第二十七步：工单工序关系化与全库待检池验收

结论：工单工序已建立独立关系读模型，现有JSON工序完成回填，所有后续聚合写入在同一事务内同步维护两种表示。质量页面不再依赖最近100个工单推导候选，而是查询全库待检工序。

## 数据模型

新增`work_order_operations`：

- 复合主键：`work_order_id + sequence`。
- 冻结工艺字段：工序编号、名称、工作中心和计划数量。
- 执行字段：状态、派工设备、合格数和报废数。
- 外键指向`work_orders`，删除工单时级联删除工序。
- 状态/工单/顺序、工作中心和派工设备均有数据库索引。

原`work_orders.operations` JSON暂时保留，避免破坏已有API、领域聚合和外部集成。应用服务创建或更新工单时，会在保存工单、替换工序行、写Outbox和幂等记录的同一个数据库事务中完成双写。

## 兼容迁移

迁移版本：`0017_operation_rows`。

- 先创建新表和索引，再逐个工单读取旧JSON。
- 每1000条工序批量写入，避免一次把全量工序放入内存。
- PostgreSQL与SQLite迁移链均执行通过。
- 本机原有数据回填8条工序，其中3条已完工。
- 自动化测试约束所有Alembic版本标识不得超过PostgreSQL的32字符上限。

## 全库质量候选池

新增：

`GET /api/v1/quality/eligible-operations`

候选条件：

1. 独立工序状态为`COMPLETED`。
2. 不存在相同`work_order_id + operation_sequence`的质量检验。
3. 支持工单号、生产订单、工序编号、工序名称和工作中心搜索。
4. 使用数据库分页和稳定排序。

页面右侧已升级为“全库待检工序”，支持搜索、分页和直接发起受RBAC保护的质量检验。

## 验收结果

- Ruff通过。
- mypy通过。
- 61项自动化测试通过，包含真实PostgreSQL双写事务测试。
- 真实PostgreSQL迁移头为`0017_operation_rows`。
- 最终一致性巡检比较41条JSON工序与41条关系工序，字段差异0、额外记录0。
- 实际API识别出2条待检候选。
- 实际浏览器显示2条全库候选，搜索和分页控件正常。

## 安全边界

本步只增加确定性的结构化查询能力，没有提升模型权限。发起检验仍要求`QUALITY`角色；Agent不能直接写表或绕过API。旧JSON将在读路径完全切换并经过一致性观测后，才考虑通过后续迁移移除。
