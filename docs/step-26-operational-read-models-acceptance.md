# 第二十六步：运营数据读模型与大样本页面验收

结论：设备、制造资源和质量任务已从固定前100条读取，升级为数据库筛选、分页和全量汇总。真实工厂增加数据量时，浏览器只保留当前页。

## 已完成

- 设备：按编号/名称搜索、按状态筛选、每页24条、全量健康/关注汇总。
- 制造资源：按编号/名称搜索、按资源类型和状态筛选、每页24条、全量来源数汇总。
- 质量任务：按工单ID/缺陷码搜索、按状态筛选、每页24条、全量待检/隔离汇总。
- 三类API统一返回`items/count/total/limit/offset`。
- PostgreSQL查询增加稳定的`updated_at + id`排序，避免同时间记录分页顺序漂移。
- 数据库迁移`0016_operational_indexes`增加状态/类型、更新时间和稳定ID复合索引。
- 页面模块仍按需加载；30秒轮询只刷新当前模块。

## 新增读接口

- `GET /api/v1/equipment-summary`
- `GET /api/v1/quality/inspections-summary`
- `GET /api/v1/master-data/manufacturing-resources-summary`

原有列表接口新增`offset`、`query`以及各自的`state/status/resourceType`筛选参数。

## 目标对齐

本步没有扩大Agent生产权限。模型仍只负责解释与提案，确定性策略、身份、审批、版本和设备联锁仍是生产动作的最终边界。此次改造直接解决了通用MES面对大量设备、刀具、夹具、程序、量具和质量任务时的可用性问题。

## 下一决策门

“待检工序”目前明确限定为最近100个工单的候选窗口。要实现全工厂范围、可查询、可排队、可由Agent安全消费的待检池，需要把工单JSON中的工序拆成独立的`work_order_operations`关系表，并进行一次兼容迁移。这属于核心数据模型升级，应在实施前确认。
