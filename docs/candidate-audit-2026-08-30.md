## 结论

### OpenMES

三者中功能覆盖最广，存在 PostgreSQL、REST API、MQTT、OPC UA 网关、审计和容器部署结构，适合做业务能力和界面参考。

但是当前版本为 AGPL-3.0。若修改后通过网络向用户提供服务，通常会触发相应源代码提供义务。对于计划闭源销售的商业产品，它不能在未完成法律评估、隔离设计或商业授权的情况下作为主代码底座。

处置：保留为功能基准和可选开源发行路线；暂不复制其代码进入自主核心。

### point85/mes-ai

其结构最接近本项目目标：FastAPI、版本化 REST API、WebSocket 事件、产品/工艺/WIP/谱系、ERP和设备模拟器、插件以及 OPC UA/MQTT 等可选集成。

但是固定版本的仓库根目录没有发现 LICENSE。公开可读不等于允许复制、修改和商业使用。

处置：可阅读其公开思想和接口形态；在作者补充明确许可证或取得书面授权前，不复制源代码，不将其依赖打入产品。

### Salbotics SSD-MES

MIT 许可证适合商业二次开发，核心与 API 分离清晰，包含路线、进出站、WIP、良率和产品谱系。

它定位为 SSD 产线示例，使用 .NET 10、SQLite 和简化门户；质量处置、设备协议、权限审计、机械加工资源模型和生产级运维能力均不足。

处置：可作为路线状态机和谱系实现参考，或用于快速技术实验；不直接视为完整 MES。

## 当前环境限制

- 未安装 Docker，因此尚未启动 OpenMES。
- 本机只有 .NET 6/7 Runtime，没有 SDK；SSD-MES 目标为 .NET 10，因此尚未编译。
- 本机 Python 为 3.9，而 mes-ai 要求 Python 3.12；且许可证未通过，暂不安装依赖。

这些是测试环境缺口，不是产品架构限制。安装运行时之前，先由许可证硬门槛决定是否值得继续投入。

## 选型决策

当前没有候选可以“原样成为闭源商业产品主底座”。建议采用干净实现策略：

1. 自主定义制造领域模型、事件协议、Agent 工具契约和安全边界。
2. 采用 MIT/Apache-2.0 的通用框架和组件建设模块化单体。
3. 把 OpenMES 作为功能对标，不复制 AGPL 实现。
4. 把 mes-ai 作为架构参考，未授权前不复制实现。
5. 只在确有节省价值时提取或改造 SSD-MES 的 MIT 思路，并保留版权声明。

## 下一决策门

进入代码开发前需要完成自主核心的技术 ADR：后端语言、数据库、身份认证、事件存储、模型网关和第一批 Agent 工具契约。建议主路径为 Python 3.12 + FastAPI + PostgreSQL/TimescaleDB，因为它能降低 AI/优化服务集成成本；设备侧协议可使用独立边缘网关，不强迫 MES 主体承载全部驱动。
